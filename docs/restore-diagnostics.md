# Temporary Session restore diagnostics

This temporary build records structural Session restore and scroll-jump events in the persistent VS Code **DSH Companion Restore** log output channel under the prefix `[DSH Companion restore trace]`. The initial diagnostic commit used `console.info`, which did not appear in the Extension Host log files on the affected installation; the follow-up commit connects a VS Code log channel. Remove the temporary diagnostics after the loading and scroll failures are identified; they do not alter DSH history, Session state, or the client recovery protocol.

Each line contains an opaque Session id and an event name. `panel-open` identifies a VS Code editor occurrence and Companion version; `session-bound` reports the supervised backend build. `session-state` reports open state, running, and history availability; `connection` reports transport status; `ready` marks completion of initial Client attachment. `event-window` reports the canonical change kind, `hasMore`, and counts plus first/last durable event seqs for the full window and the changed range. Transient streaming chunks have no durable seq and do not affect these counts. `batch-posted` reports sampled Webview batch ids, counts, and whether VS Code accepted the post. `batch-applied` confirms synchronous Webview dispatch returned or reports a failed batch and how many messages completed before the exception. An acknowledged batch does not prove the DOM painted correctly.

The temporary trace sends no messages, prompts, model content, tool arguments, credential values, URLs, launch tokens, or exception text to logs. A batch marker is attached to the existing Webview envelope and acknowledged only for the first eight batches, every 64th batch, reset/prepend boundaries, or an application exception. The Webview sends only its marker, processed count, and failure boolean. The Extension validates each acknowledgment at its message boundary. After one upward wheel gesture, a bounded Webview ring records only elapsed milliseconds, scroll coordinates, viewport size, follow mode, interaction flags, batch number, and fixed operation names. It reports once per editor only when the scroll position drops by at least three quarters of a viewport within two minutes; the Extension validates the complete closed numeric payload before logging `scroll-jump`. The trace distinguishes native scroll events, host message application, DOM rendering, explicit scroll writes, bounds relayout, and the next two animation frames.

To capture the scroll failure, keep the affected chat visible, let a Turn produce output, make one upward wheel gesture, and wait for the next Turn message. Note the local time and Session id. Open **View: Toggle Output**, select **DSH Companion Restore**, and find `scroll-jump` near that time. The `reason` is the first sample that crossed the threshold; compare it with the preceding `wheel-up`, `native-scroll`, host-message, write, relayout, and frame samples. A `scroll-jump` absence means either the reported movement was below the threshold, happened after the two-minute window, or the Webview did not produce a trace. The `diagnostics-started` entry proves that the persistent sink activated after a window reload. Do not send full VS Code logs without reviewing them for unrelated secrets.
